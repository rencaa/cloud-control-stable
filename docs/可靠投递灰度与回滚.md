# 可靠投递灰度与回滚

## 默认状态

`CLOUD_RELIABLE_DELIVERY_ENABLED=false`。新版本先创建附加表，但命令仍走原来的 MQTT/WS 直发路径，不改变当前业务行为。

## 启用前检查

1. 使用稳定版 EasyClick 客户端，它会持久化最近 500 个 `cmd_id` 并对重复消息只回 ACK。
2. 完成设备令牌注册；确认 WS 和 MQTT 两条链路都能鉴权。
3. 验证 `/readyz`、`/metrics`、MySQL 备份和 `command_deliveries` 表。
4. 备份数据库、上传目录和部署 `.env`。

## 灰度步骤

1. 保持开关关闭部署服务端，验证旧直发链路。
2. 在独立测试环境设置开关为 `true`，只连接一台测试设备。
3. 依次测试：普通命令、任务、客户端断网、服务端重启、ACK 丢失和重复投递。
4. 确认相同 `cmd_id` 不会重复执行，且投递状态最终进入 `acknowledged` 或可解释的 `failed`。
5. 分组逐批放量，每批至少跨越一次断线重连和一次服务重启。

ACK 表示客户端已接收并持久化命令编号，不等于长耗时业务已经完成；任务最终结果仍以 `task_status` 为准。

## 紧急回滚

```text
CLOUD_RELIABLE_DELIVERY_ENABLED=false
```

重启服务后新请求立即恢复直发。不要在紧急回滚中删除 `command_deliveries`，保留它用于审计；关闭开关后 worker 不会继续重试历史记录。

外部 MQTT 回滚时，清空 `CLOUD_MQTT_BROKER_URL`，恢复内置 MQTT 的 1883 主机端口并停止 EMQX profile。整套隔离版回滚时只停止 `cloud-control-stable`，重新启动原目录程序。

只有在功能长期停用、历史投递已备份且确认无审计需求后，才可在维护窗口人工删除附加表。删除表不是线上紧急回滚步骤。
